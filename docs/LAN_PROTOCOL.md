# 局域网互联协议（v1）

手表端（本工程）从手机端（`lx-netease-music-mobile`）整单接收歌单里的音频与歌词，全部落本地后再播放。

- **手机端 = HTTP 服务端**，同时在 UDP 上定时广播自己的地址。
- **手表端 = 客户端**，负责发现、拉歌单、逐首下载、写入本地曲库。

手机端没有某首歌的本地文件时，由手机端先自行下载，再把手表要的文件发出来（手表只调 `prepare` 轮询状态）。

---

## 1. 发现：UDP 广播

手机端每 2 秒往 `255.255.255.255:8687` 发一个 JSON 包（UTF-8）：

```json
{"service":"lxnx-lan","version":1,"port":8686,"name":"我的手机","token":"","revision":"9f2c1ab34de5"}
```

| 字段 | 说明 |
| --- | --- |
| `service` | 固定 `lxnx-lan`，手表用它过滤无关广播 |
| `version` | 协议版本，当前为 `1` |
| `port` | HTTP 服务端口 |
| `name` | 设备名，显示在手表上 |
| `token` | 配对后的 token；配对过的手表只接受 token 一致的广播 |
| `revision` | 当前对外歌单的版本指纹；手表看到它与上次成功同步的不同，会立刻开始同步 |

手表进程里常驻监听这个端口（`LanBeacon`），所以手机端点了「开始同步」手表很快就能收到；
监听没起来时（极少见）退回临时监听 5 秒。

手表绑定 `8687` 监听，收到后取 `packet.getAddress()` 作为服务地址（不用包里给的 IP，避免多网卡时给错）。
5 秒内收不到就提示「没找到手机端」。

> 手表若收不到广播：确认两端同一 Wi-Fi、路由器没开 AP 隔离；部分路由器会拦截全局广播，
> 这种情况可以在手机端补一个定向广播（对子网广播地址再发一份），或后续升级为 mDNS。

### 配对：手表出二维码，手机扫码

不配对也能用（谁广播就同步谁）；**配对之后手表只认这一台手机**，多设备或公共 Wi-Fi 下建议配对。

手表在「配对手机」页会临时开一个极简 HTTP 服务（端口优先 `8688`，被占则随机），二维码内容：

```
lxnx://p?h=192.168.1.23&p=8688&c=482913
```

| 参数 | 说明 |
| --- | --- |
| `h` | 手表的 Wi-Fi IP |
| `p` | 配对服务端口 |
| `c` | 6 位一次性配对码（同时显示在二维码下方） |

手机扫码后调用：

```
POST http://{h}:{p}/pair
Content-Type: application/json

{"code":"482913","deviceName":"我的手机"}
```

成功返回：

```json
{"ok":true,"token":"9f3c...32位hex","watchName":"OPPO Watch"}
```

之后：

- 手机把 `token` 存下来，广播包里带上它，**所有 HTTP 请求都要带 `X-LX-Token: <token>`**；
- 手表发现阶段就丢弃 token 不匹配的广播，服务端也可校验请求头；
- 换手机或想重新配对：在手表「配对手机」页点「解除配对」。

配对服务只在该页面打开时运行，离开页面即关闭，端口每次可能不同，以二维码为准。
`GET /pair/info` 会返回手表名、端口与配对码（调试用），`GET /ping` 返回 `{"service":"lxnx-pair"}`。

## 2. HTTP 接口

所有路径都相对 `http://<phone-host>:<port>`。响应统一 UTF-8。

### `GET /api/ping`

握手探测，任何情况下都返回：

```json
{"service":"lxnx-lan","version":1,"name":"我的手机"}
```

### `GET /api/playlist`

返回手机端**当前选中的歌单**（顺序即播放顺序）：

```json
{
  "playlistId": "8842",
  "playlistName": "我喜欢的音乐 + 通勤",
  "revision": "9f2c1ab34de5",
  "quality": "320k",
  "playlists": [
    { "id": "local:8842", "name": "我喜欢的音乐", "songIds": ["1234567", "1234568"] },
    { "id": "wy:7654321", "name": "通勤", "songIds": ["2200111"] }
  ],
  "songs": [
    {
      "id": "1234567",
      "name": "歌名",
      "artist": "歌手",
      "album": "专辑",
      "duration": 233000,
      "audio": { "ready": true, "ext": "mp3", "size": 8123456 }
    }
  ]
}
```

- `playlistId` / `playlistName`：本次同步的合集标识与名称（多个歌单用 ` + ` 拼起来）。
- `playlists`：**按歌单分组**，手表左侧那页据此列出「有哪些歌单」，点进去再按 `songIds`
  的顺序列歌。同一首歌出现在多个勾选歌单里时，每个歌单的 `songIds` 都会带上它（文件只存一份）。
  没有这个字段时，手表把整份曲库当成一个歌单显示。
- `revision`：**歌单内容指纹**，只要歌单内容（曲目集合、顺序、分组）没变就必须保持不变。
  手表靠它判断「要不要重新传」，不能每次请求都换一个值，否则每次都会全量重传。
  推荐算法：对 `id:size` 排序后拼接再取哈希；歌单被换掉或增删曲目时自然变化。
- `id`：歌曲唯一标识，手表用做文件名与缓存键，**必须是 `[A-Za-z0-9_-]`**。
  手机端不要拿中文标题清洗后当 id（不同歌会撞成同一串下划线），用数字 id 或标题哈希最稳；
  手表端对含非 ASCII 的 id 会额外补一段 8 位哈希兜底。
- `audio.ext`：`mp3` / `m4a` / `flac` / `wav` / `aac`，决定手表落盘后缀。
- `audio.size`：字节数，手表用它判断缓存是否完整；填 `-1` 表示不校验。
- `duration`：毫秒，可为 0。

### `POST /api/prepare/{id}`

让手机端确保这首歌的音频已在本地。手机端处理：

1. 本地已有文件 → 立刻返回 `{"state":"ready"}`
2. 没有 → 开始从上游下载，返回 `{"state":"preparing"}`，手表每秒重试一次
3. 下载失败 → `{"state":"failed"}`

手机端**不要阻塞**在这个请求里等下载完成，否则手表会读超时（15 秒）。

服务端不实现该接口（返回 404）时，手表按「可直接下载」处理。

### `POST /api/skip/{id}`

手表端本地**已经有这首歌的完整文件**、这一轮不需要手机准备时调用。
手机端把这首标成「手表已有」，列表里不再显示「待准备」；不会触发下载。

- 返回 `{"state":"skipped"}`
- 服务端不实现（404）时手表直接忽略，同步照常

### `POST /api/finish`

一轮同步结束（正常完成、清空、用户取消）时调用，body：

```json
{"total":300,"downloaded":3,"skipped":297,"removed":2,"cancelled":false,"message":""}
```

手机端据此：把界面从「同步中」切成「已完成」并显示统计；
**如果没有歌单开着自动同步，顺手把服务停掉**，用户不用再手动点「停止同步」。
还有歌单开着自动同步时服务继续运行，继续盯歌单变化。

服务端不实现（404）时手表忽略，回退到旧行为（手机端一直显示运行中）。

### `GET /api/audio/{id}`


返回音频字节流。要求：

- 支持 `Range`（`206 Partial Content`），便于断点续传；不支持也能用，只是重试要整首重来
- 必须带 `Content-Length`
- `Content-Type` 用 `audio/mpeg`、`audio/mp4` 等

### `GET /api/lyric/{id}`

返回 LRC 文本（`text/plain; charset=utf-8`），没有歌词返回 `404`，手表显示「暂无歌词」。

### `GET /api/cover/{id}`

返回封面图片（建议 JPEG），没有返回 `404`。

## 3. 同步时序

```
手表                                        手机
 |-- UDP 监听 8687 -------------------------> | 每 2s 广播 beacon
 |<---------------------------- beacon ------|
 |-- GET  /api/ping ------------------------> | 可选，确认服务
 |-- GET  /api/playlist --------------------> |
 |<---------------------- songs[] -----------|
 |   for each song:
 |-- POST /api/prepare/{id} ----------------> | 本地没有就先下载
 |<-------------------- {"state":"ready"} ---|
 |-- GET  /api/audio/{id} ------------------> |
 |<------------------- audio bytes ----------|  写 lan_library/{id}.mp3
 |-- GET  /api/lyric/{id} ------------------> |
 |-- GET  /api/cover/{id} ------------------> |
 |   写 index.json，刷新播放列表              |
 |-- POST /api/skip/{id} -----------------> | 本地已有的曲目：只通报，不传输
 |-- POST /api/finish ---------------------> | 带统计；手机端结束任务、按需自动停服务
```

断点：音频先写 `.part` 再改名；`index.json` 每完成一首就落盘，中途取消已接收的歌曲照样可用。

### 自动同步（手表端行为）

手表不需要用户点任何按钮，下面三种时机自动触发一次对齐：

1. 应用启动后约 2 秒；
2. 系统网络状态变化（例如刚连上 Wi-Fi）；
3. 每 10 分钟定时检查一次。

每次检查的流程：

```
没连 Wi-Fi → 直接跳过（不打扰用户）
连上 Wi-Fi → UDP 发现（最多 5 秒）
      发现到手机 → GET /api/playlist
      revision 与本地一致 且 本地曲目数一致 → 什么都不做
      否则 → 先删掉不在本次清单里的文件 → 重建歌单结构 → 逐首补齐（已缓存的跳过）→ 收尾清理
```

要点：

- **清单即权威（唯一真相）**：手表上的曲库以手机端下发的清单为准 ——
  清单里有哪些歌单、哪些歌，手表就留哪些；不在清单里的一律删掉。
  由此推出三条结论：
  ① 手机端取消勾选某个歌单 → 手表上这个歌单和它的音频、封面、断点文件全部删除；
  ② 同一个歌单多次同步时，上一次勾选过、这一次没勾选的歌 → 同样删除
     （手机端每次手动同步都用「这一次的选择」整体覆盖该歌单的基线，不是取并集）；
  ③ 手机端勾选了某个歌单但这次一首歌都没选 → 手表上保留这个歌单，显示「0 首」，不删歌单。
  旧版索引、手工放进目录的文件都不受保护，同步收尾照样按清单清理。
- **清单不完整时宁可不同步**：手机端只要有任意一个勾选的歌单没读出来（网络、登录、
  歌单被删），这一轮就不重算清单 —— 手动同步直接报错中止，后台自动同步跳过本轮。
  因为清单变短会被手表理解成「这些歌不要了」，半份清单等于误删。
- **先删后建，再逐首加歌**：拿到 `/api/playlist` 后按顺序做三件事——
  ① 清掉「本次清单里没有」的歌的文件（手机端取消勾选的歌单、歌单里删掉的歌），
  只删文件不动索引，清单里还有的歌的 `.part` 断点保留；
  ② 把 `playlists` 里的歌单写进
  `index.json`（每个歌单的 `songIds` 都是完整的，只是音频还没到），并通知歌单页刷新。
  这时左侧歌单页已经能看到这些歌单、曲目数从 0 开始；之后每落盘一首就重写一次索引，
  该歌单的曲目数跟着涨，点进去能直接播已经到位的歌。整份传完才算同步完成。
  所以手动同步时，手表左侧的歌单列表在很短时间内就会变成「这次勾选的那些」——
  没勾的已经消失，新勾的已经出现，音频随后陆续到位。
- **已同步过的曲目不重复传输**：每一轮同步，手表先看曲库目录里有没有这首歌的完整音频 ——
  有就整首跳过（不问手机要 `prepare`、不拉音频），只做索引记账。判定规则：
  优先按清单给的扩展名找同名文件；找不到再按曲目 id 前缀找其它扩展名（手机端换过音质回退、
  封装变化导致 `ext` 变了，但文件还是同一首歌的成品，直接复用）。只有「文件不存在、0 字节、
  或手机端明确给了大小且长度对不上」才算没同步过，才会真的传。
  所以自动同步、手动再同步、甚至歌单顺序变了导致的整份重算，都不会把已有音频重传一遍。
- **增量**：只下载本地缺失或大小对不上的音频；歌词/封面已有就不再拉。
- **顺序跟随**：本地 `index.json` 的 `songs` 顺序就是手机端歌单顺序。
- **删除同步**：手机端歌单里被移除的歌，手表会删掉对应文件，避免越积越多。
  同步收尾时按「本次清单里应该有哪些 id」扫一遍 `lan_library/`，凡是不在清单里的
  音频、封面、断点残留（`*.part`）全部删掉 —— 手机端取消勾选某个歌单后，
  那个歌单的歌就是这样从手表上消失的（索引里没有记录的孤儿文件也一并收拾）。
  中途取消的同步不清理，等下次完整跑完再删。
- **清空**：手机端一个歌单都没勾时点「开始同步」，服务照样起来并下发一份 `songs: []`、
  `playlists: []` 的清单。手表收到后按上面的 prune 逻辑把 `lan_library/` 里所有音频、封面、
  断点残留删干净，`index.json` 写成空清单，同时停掉当前播放（不然 MediaPlayer 还握着
  已删除文件的句柄会继续出声）。`songs` 字段缺失（不是空数组）才当作协议不对，不动本地曲库。
  清空只由「开始同步」触发：手机端后台轮询（60 秒一次）在勾选为空时直接跳过，
  免得「取消 A、再勾上 B」的中间状态把整库删掉重下一遍。
- **不打断播放**：正在播的那首如果还在新歌单里，索引会按 `id` 保持；同步过程不会主动发声，
  新歌单要等用户按播放或切歌才生效。
- **边下边听**：每下完一首就写索引并刷新播放列表，所以不必等整份歌单传完 —— 已经传完的歌
  随时能在播放器页按播放，或者从左侧歌单页点着播。索引里的音频都来自 `.part` 改名的成品，
  不会把正在写的半截文件列进去。
- **同步在后台跑**：同步属于进程级任务（`LanSyncManager` 单例），退出「连接手机」页只是
  断开界面回调，传输继续；再进这页会重新挂上并显示当前进度。只有按「停止」才真的中断。
  播放列表整体替换是「先建新表再整体换」，界面不会读到半空的列表。
- **失败静默**：找不到手机、超时都不弹窗，等下一轮再试；手动进入同步页才看得到错误。

本地 `index.json` 结构：

```json
{
  "playlistId": "8842",
  "playlistName": "我喜欢的音乐 + 通勤",
  "revision": "9f2c1ab34de5",
  "syncedAt": 1792336857000,
  "playlists": [
    { "id": "local:8842", "name": "我喜欢的音乐", "songIds": ["1234567"] },
    { "id": "wy:7654321", "name": "通勤", "songIds": ["2200111"] }
  ],
  "songs": [
    { "id": "1234567", "name": "歌名", "artist": "歌手", "audio": "1234567.mp3",
      "cover": "1234567.jpg", "duration": 233000, "lyric": "[00:00.00]..." }
  ]
}
```

`playlists` 原样来自手机端清单，歌单页第一层按它列歌单（名称 + 曲目数 + 首曲封面），
点进去用 `songIds` 里的 id 去 `songs` 取曲目；缺失的（还没下完 / 已被清理）自动跳过。
手机端没给这个字段时，`LanLibrary.readPlaylists` 会把整份曲库当成一个歌单返回，界面不至于空着。

## 5. 手机端实现（RN，`lx-netease-music-mobile-main`）

| 位置 | 作用 |
| --- | --- |
| `android/.../lanserver/LanServerModule` | 原生 HTTP 服务（8686）+ UDP 广播（8687），`Range` 断点续传 |
| `src/core/lxxwear/sync.ts` | 勾选歌单 → 组装清单 → 启动服务 → 处理 `prepare`（准备音频/歌词/封面） |
| `src/core/lxxwear/playlists.ts` | 可同步歌单（本机列表 + 网易云收藏） |
| `src/core/lxxwear/config.ts` | 勾选结果、音质、自动同步的持久化 |
| `src/screens/Home/Views/LxxWear` | 侧边栏 LXXWear 页面 |

要点：

1. **原生只负责发文件**。`/api/ping`、`/api/playlist`、`/api/audio|lyric|cover/{id}` 都由原生直接答，
   `prepare` 不在这里下载，而是抛 `LXXWearPrepare` 事件给 JS，JS 用 App 现有的取地址/下载能力准备好之后
   回调 `setReady(id, path, ext, size, lyric, coverPath)`，状态才会变成 `ready`。
2. **手机没有文件时先自己下载**：先看 App 下载记录里有没有同音质的成品文件，有就直接发；
   没有再按 `master → hires → flac → 320k → 128k` 逐级降级取地址下载到 `DocumentDir/lxxwear/audio/<音质>/`。
   歌词走歌词接口，封面走封面地址，失败都不影响音频。
3. **音质换了要重传**：清单里每首歌的 `id` 带音质后缀（`wy-123456__320k`），
   换音质等于换了一批 id，手表按 id 落盘，旧文件会被当成「歌单里已经没有的歌」删掉。
   `revision` 也把音质算进去，所以手表一定会重新拉。
4. **断点续传**：手机侧的文件是整份准备好的（同一 `id` 每次给同一份字节，且支持 `Range`），
   手表侧 `LanClient.download` 会把没下完的留在 `.part`，下次带 `Range: bytes=N-` 接着要，
   已完成（大小对得上）的歌直接跳过，所以中止后重来不会从头传。
5. **自动同步**：勾上后 App 启动 8 秒会把服务拉起来。服务只要在跑，手机端就每 60 秒重算一次清单
   （选中的歌单里有网易云歌单时降到 3 分钟一次，因为要过网络），`revision` 变了就通过广播下发；
   在手机界面改勾选则立即重算，不用等下一轮。
   手表侧 `LanBeacon` 常驻监听广播，看到 `revision` 与自己上次成功同步的不一致就立刻开始同步，
   不用等 10 分钟轮询。
6. **取消勾选 = 删除**：某首歌只属于被取消的歌单时，新清单里没有它的 id，
   手表同步收尾会把它的音频、封面、歌词一起删掉；歌词本来只存在索引里，重写索引就没了。
7. **端口**：8686 起，最多试到 8695；实际端口写在广播包里，手表以广播为准。
8. **鉴权**：配对过就带上 token，广播和请求头都要对得上；没配对时 token 为空，不做校验。

## 6. 自测：电脑上跑模拟服务端

不需要手机端也能验证手表端：

```bash
python tools/mock_server.py --media tools/mock/media
```

它会扫描 `--media` 目录下的音频与同名 `.lrc`，在本机 `8686` 起 HTTP 服务、`8687` 发 UDP 广播：

- 文件名建议 `歌手 - 歌名.mp3`，会拆成 artist / name；同目录放 `歌手 - 歌名.lrc` 作为歌词
- 同名 `.jpg` 作为封面
- 手机（或手表）和电脑在同一 Wi-Fi，手表进「控制台 → 同步图标」即可整单拉取
- 电脑防火墙记得放行 8686（TCP）与 8687（UDP）
